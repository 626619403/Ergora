# Select specialists before freezing a development task

The three development presets share one preparation default: module (`ergora-refactoring-engineer`), validation (`ergora-compatibility-validator`) and the canonical coordinator in both inventory and plan. Their work graphs remain different. With three final reviewers, the default large-change graph needs 13 model slots; governance and refactoring each need 11. Selecting a task type does not change the shared preparation graph.

This fixed example revises large-change for an actual cross-end interface change. [publish.py](publish.py) uses the existing `definitions.workflows.revise` API and immutable libraries. It installs the current preset, follows its real root → delivery → preparation references, and obtains specialist versions and digests from that installation's receipts. It preserves the selected sources' resources, permission ceilings, limits, work and review references. It publishes new task-specific IDs, leaving source packages and stored frozen tasks intact.

Inventory runs contract, server, client and validation inspectors independently. Planning starts contract and validation planners from the canonical inventory; server and client planners wait for and consume the complete contract output. In each group, `expert-results` joins all four experts, the coordinator consumes that complete join, and `done` explicitly joins all four experts and the coordinator. The original Executor supplies canonical inventory to every planner; the preparation wrapper keeps its two root-task inputs independent. The coordinator reconciles the proposed contract with validation obligations and records unresolved conflicts before owner approval.

The supervisor retains one owner per direction and aims for 4–8 experts actively doing assigned work. This fixed example has four independent inventory experts, while planning and work have at most two independent experts and final review has three. Select suitable assignments before freezing when the task warrants them. Report the actual count and blocker and retain the existing dependencies and budget.

Run from the repository root using the current Ergora Python environment and an explicit definition-library home:

```bash
python examples/composition/development-specialists/publish.py \
  --home ./cross-end-library --version 1.0.0 > ./cross-end-receipts.json
```

Use a new receipt filename and an unused version when changing this task revision or its source packages. Each publication is immutable and independent; a failure can leave already published children, and the same exact publication can be reconciled by its receipt. The script publishes inventory and plan first, then preparation, delivery and the sole native parent. Every replacement reference comes from the preceding real publication receipt. The final preview is accepted by `freeze_manifest`; the returned JSON saves the exact installation, bases, publication receipts, final root, preview identity and complete manifest receipt. This is static definition publication, without model execution or plan approval.

Copy [task.example.json](task.example.json), set `composition.manifest` to the receipt's `manifest.path` and `composition.manifest_digest` to its `manifest.digest`, and replace the issue, task ID, exact baseline and illustrative contract/paths with verified project facts. The invalid placeholders intentionally prevent execution. Use the original [prepare → preview → dual-digest create lifecycle](../../../docs/development/preparation.md#prepare-under-a-single-budget-authorization), then start and approve the exact canonical plan through that task's original owner. Registered Linux/WSL2 execution, task-MCP and the declared trusted current-container writer boundary are required; definition installation establishes none of their availability or authentication.

The work split keeps one writer per original unit. Contract owns the interface specification and shared fixture; server and client write separate implementation paths after contract; integration-tests waits for both and owns only its assigned tests and validation notes. Methods remain in the existing Agents and their inherited Skills. The fixture and implementation directories must match the real repository; overlapping write prefixes require a smaller owner or an actual serial dependency. The unchanged trusted integrate and verify stages run before independent review of the same final candidate.

This graph has 5 inventory + 5 plan + 4 work + 3 review = 17 finite model slots. Coordinators consume slots. The task example's writers use `gpt-6.2-sol/max`, satisfying the Agent-level floor also required by their planner role. Preparation is read-only. Add any applicable required or explicitly advisory review before freezing and increase the budget by the actual added leaf count; excluded experts have no empty leaf. All actual members must finish under the one original clock and cleanup reserve. Unknown calls retain their original identities for reconciliation. Review proposals can be batched or appended for later supervisor-managed tasks; they do not alter this frozen graph, slots or deadline.

For a governance task, use the same revision sequence with `repository-governance` as the installed source. Select governance-mapper and architecture-test-author for inventory; select refactoring-engineer and architecture-test-author for plan. Both groups use `expert-results` over their two experts, coordinator consuming that join, and `done` over those experts plus coordinator. Retain the source's knowledge-map and boundary-test work units, disjoint ownership and three reviews: 3 + 3 + 2 + 3 = 11 slots. A deliberately smaller one-member preparation group retains an explicit `done` all-join covering its coordinator, with the group result pointing to `done`. Save the actual publication receipts and recalculate all selected leaves for either revision; these choices are explicit task revisions.

Only a refactoring descendant inherits the refactoring root's codebase-quality Skill. A link to that method does not add its bytes or permissions to a large-change or governance task. Required extra resources must be published through their real ancestor and included in the final manifest. Missing members, incomplete ports, wrong candidates, unsupported operations, cancellation and unconfirmed cleanup remain visible blockers under the original six-stage contract.

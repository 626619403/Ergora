# Component change protocols

English · [Documentation](../README.md)

This page is for Agents and maintainers changing the Ergora repository. First restore the current plan under the root [collaboration rules](../../AGENTS.md), then select the corresponding component below. User installation/operation remains governed by the [task guide index](../README.md) and domain guides; this page does not repeat command parameters.

## Choose the actual change point

|What changes|Owners and actual consumers to read first|Section|
|---|---|---|
|Which model/CLI a role invokes|`configuration.catalog`, `configuration.bindings`, `agents.backends`; consumers `agents.invocation` / `agents.runs`|[Agents and external sources](#agents-and-external-sources)|
|Issue platforms and original PR/MR associations|`issues.backends`, `issues.identity`; consumers `issues.application`, `issues.writebacks`, `development.review.sources`|[Agents and external sources](#agents-and-external-sources)|
|Roles, specialties, nested templates, Skills/MCP/context|`definitions.agents`, `definitions.workflows`, `definitions.bundles`, `agents.mcp`|[Definitions and complete resources](#definitions-and-complete-resources)|
|Project configuration, persistent formats or migrations|`configuration.projects`, `configuration.registrations`, `configuration.validation`, `storage.state`; corresponding domain consumers|[Configuration and persistent formats](#configuration-and-persistent-formats)|
|Formal task/training execution, approval, cancellation, recovery or results|`development.application`, `training.application`, their native clients/runtime owners and shared process/budget resources|[Execution and evidence](#execution-and-evidence)|
|Memory, Skills, evaluation, search or retrospectives|`improvement` domain owners, `definitions.skills` and `development.context`|[Improvement and optional tools](#improvement-and-optional-tools)|
|CLI, HTTP or page interaction|`interfaces.cli`, `interfaces.web`, `data/console`, calling the same domain use cases|[Interaction entry points](#interaction-entry-points)|
|Installation, upgrades, platform scripts or validation|`scripts`, `tests` and explicit CI groups|[Scripts and checks](#scripts-and-checks)|

Before adding/changing/removing anything, find an actual “configuration → construction → invocation → result → recovery” path; record observable behavior, callers, and existing alternative interfaces. Keep implementation-specific configuration, initialization, and behavior with their owner. Implement an existing shared contract directly when sufficient; design family-specific construction/execution interfaces only when real interchangeable implementations exist without a contract. Ordinary data branches, mathematical branches, and one actual extension function do not thereby require an ABC. New files should hide concrete invocation obligations rather than merely wrap one call in forwarding.

For behavior-preserving reorganization, retain configuration, persistent formats, and failure/recovery semantics; algorithm or capability extensions require a separate acceptable slice. During development, converge directly on the current interface, migrate actual consumers first, and remove invalid dispatch and compatibility-only tests. Original records retain their actual identity; explicitly report limitations when no current reader is available, without adding old execution paths. Every guard must correspond to a reachable failure involving external input, persistent identity, resources, or concurrency, handled at the boundary that truly owns the invariant.

## Agents and external sources

The shared Agent backend interface is [AgentBackend](../../src/ergora/agents/backends.py); that file's `_BACKENDS` and `for_binding` own selection. [agents](../../src/ergora/agents/invocation.py) calls the same interface and owns result schemas and process results. To extend an actual backend:

1. Implement native commands, stdin, result extraction, diagnostics, and actually supported modes. If archiving or continuation is supported, add original session identity and resource recovery under the interface. When [CommandBackend](../../src/ergora/agents/backends.py)'s `stage-json-v1` already satisfies the requirement, use the existing configurable command entry first.
2. Register in the family factory and, where needed, declare configuration/role capabilities and platform support in the [component catalog](../../src/ergora/data/components.json); optional SDKs still belong in extras or separate tool environments. `agents`, task scheduling, CLI, and pages continue to call the shared interface, without adding another dispatch path by new backend name.
3. Validate changed modes at the actual construction/protocol seams of existing [Agent tests](../../tests/test_agents.py), covering real failures rather than only literal argv assertions. Record `available`, credential presence, mode admission, actual invocation, and business acceptance separately; unsupported modes fail explicitly. Different-backend review is a preference, and fallbacks retain actual reasons.

Issue sources use [IssueBackend](../../src/ergora/issues/backends.py) and its family factory; [source identity](../../src/ergora/issues/identity.py) owns normalization of API bases, repository namespaces, and number/iid. Original IDs, repository-local numbers, and complete text cannot be interchanged or truncated. Validate pagination, drift, native responses, and reachable errors through the [issue seams](../../tests/test_project_issues.py); explicit same-repository PR/MR collection uses the [review-source owner](../../src/ergora/development/review/sources.py) and [material guide](../review/materials.md). It reads native repository/request observations and complete local Git objects. Forks, remote source search, automatic comments and merged GitHub PR collection remain unsupported; existing candidate associations cannot replace source collection.

Handle read-only collection separately from external writes. New comment/label actions belong to [issue_writebacks](../../src/ergora/issues/writebacks.py)'s domain action contract, preserving original intent/attempt/receipt and unknown reconciliation; platform protocols remain in IssueBackend. Without explicit write requirements and existing authorization, implement local reports only, without posting comments, approving, or merging by default.

## Definitions and complete resources

Definitions/schemas/presets live in `data/presets` and `data/schemas`; library/compilation belong to the [definition owner](../../src/ergora/definitions/workflows.py) and [complete bundle owner](../../src/ergora/definitions/bundles.py). For changes limited to roles, specialties, existing backend selection, serial/parallel graph relationships, Skills, and context, prefer [definition editing/revisions](../definitions/agents.md) and [workflow composition](../definitions/workflows/compose.md), without Python changes.

Published IDs/versions/digests and manifests are immutable contracts. Content changes raise the current bundle's published version and update actual references/catalogs, avoiding conflicts with published identities. Source retains one bundle and execution entry per current semantic behavior; stored objects and frozen inputs retain original identities without old runtime routes added for them. Complete resources include bodies, all Skill files, ordinary attachments, directories, and executable bits, with identities checked through original preview/accepted candidate/publish. Reuse `DefinitionLibrary` and `asset_trees` rather than implementing another copier/digester/publisher.

Child instances read all ancestor Skills and context, with permissions narrowing at each level; adding materials grants no tool or network authorization. When added resources require higher permissions, adjust necessary parents and children together and preview again rather than bypassing the parent template. Existing compilation/resource owners validate duplicate Skill names, paths, attachments, and capacity. Repository `AGENTS.md` guides only source collaboration and does not automatically become template runtime grants, MCP, or resources.

New presets use the [existing freeze/install regressions](../../tests/test_presets.py) to protect old definitions and new bundle completeness; compilation changes use [composition tests](../../tests/test_workflow_definitions.py) to validate actual inheritance/reference/graph consumers. A single leaf `prepare/run-input` does not automatically run predecessors or collect ports. The [standalone graph route](../definitions/workflows/compose.md#run-a-standalone-workflow-graph) admits its supported read-only graphs. Formal execution applies the original selected-route and candidate requirements. Ordinary proposals do not become formal candidate approvals.

## Configuration and persistent formats

[components](../../src/ergora/configuration/catalog.py) reads component metadata; [bindings](../../src/ergora/configuration/bindings.py) checks family bindings; [projects](../../src/ergora/configuration/projects.py) owns project revisions; [registrations](../../src/ergora/configuration/registrations.py) owns formal project registration and projection of original configuration. New configurable variables must explain default/old omitted-value semantics and actual readers; do not lock valid configuration to one default for tests.

Structural validation uses [contracts](../../src/ergora/configuration/validation.py) and corresponding versioned schemas; cross-field, content identity, and lifecycle constraints remain with domain owners. Definition editing JSON/YAML uses the original strict converters; YAML is a definition input form, not an executable Python recipe or permission for arbitrary imports. Binary attachments retain original bytes; digest algorithms, canonical JSON, original file SHAs, executable bits, and complete Git OIDs each follow their original contracts rather than being unified into a “general hash.” Secrets use only environment variable references, never configuration snapshots, prompts, reports, or examples.

SQLite is accessed only through [State](../../src/ergora/storage/state.py) and domain transactions; persistent semantic changes require consideration of schema versions/old-writer isolation, backup, recovery, and rollback. Index libraries, original intents, and external training records also have their own file contracts, which SQLite migrations cannot implicitly rewrite. Check actual compatibility through [migration](../../tests/test_state_migrations.py), [backup](../../tests/test_state_backups.py), and corresponding schema/domain seams; adding an ordinary configuration field does not automatically require a new table or migration of all history.

## Execution and evidence

[tasks](../../src/ergora/development/application.py) and [training](../../src/ergora/training/application.py) provide application entry points; native operation processes load the selected registration configuration. Versioned [WorkflowInput](../../src/ergora/development/inputs.py), original Temporal, and executor/job/process/budget owners handle execution/cancellation/recovery. First locate the concrete owner through the [current architecture](current.md) and [reference boundary](reference-boundary.md); UI, CLI, and new proposal templates do not own a second runtime state.

New external operations preserve attempt-before-send and original IDs/complete intents/receipt identities. A lost reply means unknown and requires reconciliation through the original run/history first; restarting, changed current configuration, or a missing successful receipt does not justify resending. Budget changes must check cross-stage behavior, recovery, descendant process stopping, and cancellation rather than constraining only one model call. Choose existing seams with these transitions from corresponding `test_task_*`, `test_budget_*`, or `test_training_*`. Managed training's explicit request/single launch belongs to `training.runtime.execution`; cross-interpreter complete records/provenance and offline observation belong to `training.execution_protocol`. Preserve final admission within the original lock, the original clock, and the sole reaper. No spawn is allowed after a stop frame; missing selected installations must not block historical reads. Durable confirmation must synchronize and reread the same existing chain, without fabricating stop proof or granting execution again.

Training manifests/baselines/runners, comparison gates, quality constraints, archiving, and exact approval remain with original owners; the [multi-round index](../../src/ergora/training/rounds.py) only links original observations and does not execute optimization, advance baselines, or grant approval. Flowcharts, kernel designs, and measurement suggestions are not actual execution. Kernel evaluation remains in the overall proposal path, allowing no kernel changes. New performance claims must bind original baseline/candidate, fixed workloads and quality oracles, environment, paired raw data/measurement windows, and gain uncertainty; CPU contracts cannot accept real GPU behavior or training quality.

Current controller consent is schema5 and explicitly selects strong full-accepted execution or bounded screen/profile/no-effect-skip; manual schema1 remains distinct, and current search/cycle inputs are schema2. Preserve one current workflow/worker interface and the original parent permits, attempt-before-send, irreversible stop, separate durable confirmation/drain/executor-cleanup facts and sole reaper. Existing saved records retain data-only scope without defaults, replay or renewed clocks.

The original materials/configuration/preparation owners produce source/input conformance C and exact-preview acceptance A; neither preparation nor a full-role record grants D1 full execution. Preserve same-owner durable CPU references, complete context/source/subject checks, strict capacities, atomic no-effect skip and source-owned diagnostic/read-only analyst caps. Missing required evidence or unknown cleanup blocks advancement; unsupported allocation matching remains visible. See the [training ownership and recovery contract](execution/training.md#original-training-budget-submission-and-deadline-owner) and [bounded CPU task contract](../training/controllers.md#bounded-cpu-search-and-per-round-diagnostics) for current joins and scope. Source, package, controlled ports, real services/models and GPU/business acceptance remain separate.

This repository does not own target training frameworks' optimizer, model, dataset, loss, or forward implementations. When developing/refactoring a target project, first identify its native component construction and training/checkpoint calls, then add local protocols in the **actual component directory**: extensible interfaces/configuration, tensor/sample/mask/normalization/state obligations, algorithm/data semantics that must not change implicitly, invocation/resources/recovery, minimum numerical/gradient/parallel checks, and locations of existing examples/base classes. Write protocols in the target project's own docs and directories; Ergora templates do not generate them automatically or directly modify unauthorized business repositories.

Choose the target project's actual extension seam and preserve its normalization, communication, parameter and recovery obligations. Verify that the selected interface is current in that project's source; a deprecated compatibility interface is not a new extension point. These control-plane protocols introduce no production trainer dependencies.

## Improvement and optional tools

[memory](../../src/ergora/improvement/memory.py) owns memory validity/revisions; [skill_assets](../../src/ergora/definitions/skills.py) owns Skill content/heads; [evaluation](../../src/ergora/improvement/evaluation.py) owns trusted suites/evaluation; [retrospectives](../../src/ergora/improvement/retrospectives.py) owns generation/candidate export. [task_context](../../src/ergora/development/context.py) owns material selection and initial freezing; recovery uses original frozen inputs. Candidate generation, static checking, actual evaluation, explicit adoption, and rollback are distinct operations; generators cannot change trusted suites or substitute current heads into historical tasks.

GEPA text search, research sources, mirrored memory, and native kernel tools have actual selection/lifecycle owners in `optimization`, `research` / `scheduling`, `memory`, and `kernel` respectively. These domains are not all unified under one ABC/plugin bus. Check existing support and actual consumers first; when a multiple-implementation seam is needed, define a slice in its own family rather than adding a universal tool dispatcher to scheduling. Report optional tool declarations, installation, native identity, authentication, supported operations, and actual execution separately; state specific gaps when unavailable rather than pretending success.

## Interaction entry points

[CLI](../../src/ergora/interfaces/cli.py) and [HTTP](../../src/ergora/interfaces/web.py) only parse transport inputs and call the same use cases. Domain identity/permissions/scoring/publishing/recovery remain with owners, and pages do not copy those state machines. `data/console` follows existing view interfaces; reuse metadata for fields already driven by schemas/component catalogs rather than hardcoding another option table.

Asynchronous page reads preserve project, control directory, view lifecycle, and selection generation; late responses cannot overwrite newer selections. Mutation requests are submitted explicitly, with no automatic retries for failure/unknown; same-origin and request-header contracts remain intact. Index reads, complete-body reads, downloads, and actual runs each show their true coverage. UI protocol changes use original HTTP/DOM seams; use browsers for actual layout/interaction issues, without adding model tests for wording changes.

## Scripts and checks

Installation/upgrades follow existing [scripts](../../scripts) entry points, fixed tool identities, and the [installation guide](../install/linux.md). Parameters, paths, spaces, platform selection, preservation of old environments, and original intent recovery are actual interfaces; subprocesses use argv, and secrets inherit only environment references. Execution supported only on Linux/WSL2 cannot be labeled native Windows, and the current container boundary cannot be labeled OS isolation between Agents.

Select [existing tests](../../tests) and explicit groups in [scripts/ci/run.py](../../scripts/ci/run.py) according to changed behavior. Register a new file in [Linux groups](../../scripts/ci/linux-groups.json) only when it has an independent seam; do not create duplicate CI jobs for one feature. Add minimum regressions only for potential silent identity misbinding, lost results, erroneous recurrence, or recovery/resource/concurrency failures; errors clearly exposed by ordinary execution, prompt wording, and assertions mirroring implementation do not expand the matrix. Before removing tests, identify the actual seam covering their unique risk.

When installation behavior needs confirmation, build and install a new non-editable wheel, confirm actual imports from `site-packages`, then run corresponding original tests; record source passing and installation passing separately. For pure documentation or mechanical changes, check relevant links/format/complete diffs rather than repeating unchanged model, training, or full regression suites. Finally update plan/delivery under root rules, use the project's own templates and the consolidated integration/merge review described in the [review guide](../review/invoke-and-aggregate.md#choose-review-scope-and-granularity), and preserve exact source/configuration/artifact identities and untested scope; only a new candidate's own applicable CI certifies it.

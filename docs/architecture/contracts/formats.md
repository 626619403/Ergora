# Structured formats and validation owners

English · [Documentation](../../README.md)

Shared structures use JSON Schema Draft 2020-12, validated in core by `ergora.configuration.validation` using `jsonschema==4.24.0`. Business APIs accept and preserve ordinary Python JSON values; validation neither coerces types, inserts schema defaults nor reencodes through Pydantic dump. The table includes versions integrated since R2; see [architecture navigation](../current.md) for current calls. Format versions, definition semantic versions, project revisions and content digests identify different facts and cannot substitute for one another.

Structural errors use `CONTEXT at /field/0: REASON`; paths use JSON Pointer, encoding `/` and `~` as `~1` and `~0`. Missing-field or extra-field structural errors point to the containing object and list fields in the reason. Business errors still give specific reasons rather than presenting URL, file availability or scoring judgments as schema rules.

`integer` requires Python `type(value) is int`, rejecting bool and `1.0`; it also shares `number`'s finite-number predicate, preventing range keywords from skipping huge integers through inconsistent type checks. Each field declares its own bounds; native issue IDs and project revisions have only positive lower bounds, without an assumed small upper bound. `number` retains int/float values judged finite by original `math.isfinite`, rejecting bool, NaN, Infinity and huge integers outside that numeric representation range; the latter becomes a readable ValueError rather than letting OverflowError interrupt use cases. Field ranges come from original implementation (for example mini step 1–1000, cost >0 and ≤100). This is stricter than JSON Schema's default “mathematical integer” interpretation; external validators must also follow these domain semantics.

The old evaluation-version check uses `== 1`, actually accepting `1` / `1.0` / `true`; R2 retains this compatibility, still rejecting other versions. New documents and generators always write integer `1`. Any later strict version-type requirement needs a separately versioned migration; this step does not silently rewrite old inputs or digests. Unknown built-in catalog versions remain rejected at the existing loading boundary.

## Adding or adjusting fields

Change existing driver configuration structures in component configuration; forms, catalog and core structural validation take effect together with the package. Cross-field role capabilities, credentials, trusted files and approval rules remain in responsible modules; adding descriptions creates no SDK adapters. Tests should verify actual inputs/failure paths, CLI/API consistency and necessary old identities, rather than simply copying the same description into another assertion.

New format versions or digest-encoding changes require designed migration, old-client access and rollback; schema defaults, DTO coercion or dumping data again cannot replace them. The base package adds only the schema stack; Web / GEPA / Temporal and others remain optional dependencies.


## Supported task routes and material limits

The current route sets come from [application definitions](../../../src/ergora/development/application.py), [creation admission](../../../src/ergora/development/runtime/creation.py), [input selection](../../../src/ergora/development/inputs.py) and [envelope validation](../../../src/ergora/development/envelopes.py). User-definition versions and runtime-input versions are separate namespaces: definition3 can produce supported issue-source Input7, while user definition7 is unsupported. Removed formats are rejected, not relabelled as12 or routed through aliases. Original evidence stays bound to the format that produced it.

|Boundary|Current exact scope|
|---|---|
|User definition JSON|1 MiB, separately validated by the selected current definition schema.|
|Formal admission / job wire|Input12: 4 MiB (`4 * 1_048_576` bytes). Other supported inputs retain 1 MiB. `wire_limit` validates the original complete document.|
|Formal material context|Input12: 4 MiB. Other supported inputs retain 1,000,000 bytes. `context_limit` is separate from model token capacity and tool-specific input ceilings.|
|Creation contract files|Ordinary files retain 1 MiB each; `task.spec.json` uses its actual admission wire limit. The complete creation intent retains 16 MiB, including encoded complete materials.|
|Standalone composition leaf preparation|`--max-prompt-bytes` remains 1–1,000,000 bytes; bundle file/count/depth limits still apply. This is not the Input12 formal context limit.|
|Static Workflow resources|The declared `material_bytes` ceiling remains at most 1,000,000 for complete static prompts across the graph and ancestor scopes. Dynamic ports/formal context have their own checks.|
|Offline handoff|Verified Input12 manifest: 4 MiB; other manifests: 1 MiB. Each blob: 16 MiB; total deduplicated payload: 64 MiB; packet: 72 MiB; members: 4096.|

Other readers retain their own artifact/window/response limits. A 4 MiB formal transport ceiling does not enlarge a 256 KiB plan item, 16 MiB evidence artifact, standalone leaf prompt or model context automatically. See [evidence/handoff operations](../../development/evidence-and-export.md), [leaf preparation](../../definitions/workflows/leaf-calls.md) and each actual source owner before changing a limit.

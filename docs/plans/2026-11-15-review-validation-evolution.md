# Q2.4：审查 finding 复核与效果评价

日期：2026-11-15。记录基线 `3947b1e28b2cbc27ddc53cab584cced0c8d971a6`，分支 `refactor/architecture-foundations`。承接用户指定的 [Anthropic 一手文章](https://claude.dev/blog/solving-code-review-at-anthropic/)和[领域审查计划](2026-11-15-domain-review-optimization-quality.md)；[对照研究](../research/2026-11-15-anthropic-code-review-comparison.md)分别列明原文明示、源码现状和采用建议。本文仅安排后继工作，不变更已发布模板、正式批准或平台评论行为，也不阻挡当前训练控制器片的本地验收。

## 已核边界与采用决定

此前确实研究过 Claude 的官方 code-review／pr-review-toolkit、CLI、Action 和托管产品；没有证据表明现有模板直接参考了这篇特定文章。现有 `ergora-delivery-review@1.0.0` 是 structure／correctness／test-value 三路 all-join，领域根另接预训练或后训练专家；它保留每叶原意见，不是逐 finding 投票过滤。正式任务原 `reference_workflows.ReviewDAGAdapter` 可并行运行依赖图并要求独立 session；外部 PR／MR 的 `review_requests` 则准备单叶并汇集显式选择的原 run，不能把前者的自动调度能力移称给后者。

采用“找问题与核实问题分工、有限复审、真实失误驱动评价”的方法，暂不复刻其内部平台。原 finding、少数意见、未覆盖、失败和 unknown 必须保留；验证意见可以解释为何确认、驳回或仍缺证据，不能多数票删除缺陷或把不完整当通过。风险分类只能提示人工关注，不降低既有人工 release 要求。新 head 必须产生新的精确输入与审查身份，旧批准不能沿用。

## 分片、优先级与验收

|节点|现有 owner 与最小实现方向|可验收结果|进度|
|---|---|---|---|
|R0／当前|一手文章与现有源码对照；本计划、父计划及交付同步|每项区分已实现／仅有设计／待实施；来源可查，新的独立文档审查，产品与模板字节不变|本地研究／计划及静态检查完成，新的独立需求／维护性两轴approve／finding0；固定发布仍按原顺序|
|R1／P1|沿 `review_requests`、`review_dags` 和定义库增加可选的逐 finding 独立复核。先固定原候选 finding 的最小结构及来源身份，使用新版本角色／子模板和原 agent run，不改旧包、不另造调度器|同一 source／head／manifest 上保留全部原回复与 finding，逐条关联复核原 run 和源码证据；确认／驳回／缺证据可区分，缺叶／错误身份／unknown 不变为通过；用一个真实可达缺陷、一个可证伪误报和一例缺证据核完整流程。机器结构在该片具体设计中确定，不用自报置信度替代验证|待具体设计；当前外部单叶入口只接原 root task，复核输入消费者须明确实现和验收，不能只改 JSON 图就称自动可运行|
|R2／P1|沿原 `evaluation`／可信 suite 和原审查输入／结果 owner 建审查质量对照；复用已有两域 CPU 正反例作为起点，另保留已确认事故／回归的来源和答案|固定模型／模板／输入／预算；比较原三路与新增复核对已知缺陷的漏报、误报、严重性、延迟及可取得的实际成本，保留每次原输出与不确定性。效果集与候选生成分开，训练／GPU能力仍另验；没有计费观测就报告不可用，不捏造费用|待R1具体验收；既有四次真实CPU合同调用不作为质量排名或统计效果结论|
|R3／P2|沿原 review packet／source、run 与预算 owner 提供显式有界的增量复审；默认轮数上限可参考原文三轮，配置范围由真实消费者决定|第一轮保留完整原包；后轮指向前轮及新精确 head，聚焦新增 diff 但保留必要调用上下文／祖先资料与旧 finding；重复、修复、重现均可追踪。取消、耗尽或丢回复后先读原记录，不自动重跑或续预算；跨轮归并不能合并不同缺陷|待R1/R2；不在静态DAG中加回边，不先发明通用循环引擎|
|R4／P2|风险提示与可解释人工分工，沿原候选／批准／界面 owner；先做建议性标签，明确规则、来源和人工覆盖|按具体影响说明为什么需要更多人类关注，核新提交使原候选批准失效；不自动approve／merge、不覆盖人工release、不从模型票数授予权限。平台评论仍是独立、需既有明确授权的用例|待明确团队消费者；不复制原文内部0／1／2人自动放行策略|

R1开始前先重核真实消费者和现有输入／结果契约，固定小片设计、源码／配置／旧格式、验收接缝与新的独立设计审查。只为可静默漏掉身份、finding或覆盖的失败增加回归，不为每个提示句、评分阈值或排列方式扩测试矩阵。R2若暴露复核不能改善效果或成本不合适，记录结果后调整／暂停后继采用，不以“agent更多”充当优势。

R1–R4分别交付新的可选能力；当前 `review_requests.report` 的原意见和保守汇总语义保持。每个产品片运行自身适用审查模板，交新的fresh-context产品reviewer，记录原件、实际运行与未验项，再普通提交／逐片发布。具体记录见[本片交付](../delivery/2026-11-15-review-validation-evolution.md)。

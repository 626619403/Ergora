## 发布与并发合同

现有 `DefinitionLibrary` 以完整目录摘要标识对象，以 `id/version` 索引精确对象；每类库沿原 file_lock 写索引，完整对象先落地、索引原子替换。索引发布中断可留下完整未引用对象；不同正文不能占用同一版本，完全相同的重试可复用对象。这些是现有行为，不新增事务数据库或第二套定义仓库。

编辑请求固定原 `kind/id/version/digest`。完整原包（含 Skill 附件、未声明文件及空目录）必须保留，编辑生成独立候选；校验不发布版本。发布复用原 import 的当前准入：Agent 的职能/后端能力、Workflow 的完整精确依赖/祖先权限/材料/预算/端口均由原所有者校验。历史 get/export 仍可读，不因今天的后端准入变化改写旧证据。新根必须引用已完整发布且校验通过的依赖；未完成的依赖不能被新根引用为可用版本。

联合父/子修改按依赖顺序发布新版本，最后发布新根。它是逐版本可重试发布，不承诺跨库原子事务；中断时已发布的独立子版本仍可见，原根与活动任务保持旧精确引用。旧 manifest/input/审批不追溯更新。并发同版本不同正文由原不可变索引冲突拒绝；不使用页面上的“最新”版本自动覆盖或替换依赖。

## C3a 实施边界

- `definition_bundles.DefinitionLibrary.revise` 从固定基准完整 export 到控制目录内的临时目录，只重写 `agent.json` 或 `workflow.json`，由当前 inspector 检查；发布仍走原 import。返回候选身份/标准正文/资源与文件身份，不返回已经清理的临时路径。
- `agent_definitions` / `workflow_definitions` 分别构造原库，不在上层按具体 Agent 工具编写新调度分支。编辑后端只改变请求，校验/导入不调用该后端或代表认证成功。
- CLI 使用 `agent definition revise` 与 `composition revise`，显式 `--base-digest`/`--document`，`--check` 只检查。HTTP 为两类定义提供显式 revision check/publish 路径，传输只转交原用例，不复制权限、版本或身份算法。
- 不修改283冻结文件、schema/数据库、六阶段、审批/候选绑定、Temporal/原执行账本；不引入依赖、CI任务或 speculative plugin。测试聚焦此入口可能静默丢附件、绕过当前准入或发布错误版本的风险，复用原库的崩溃/并发覆盖。

每个完整实现片更新本计划/交付记录/PLAN，再用 fresh-context reviewer 审查完整 tracked/untracked 范围和实际证据，并实际运行 Ergora 自身模板。发现问题保留原红，最小修正后同片复核。普通提交推送按候选自身的必要 CI 和明确 HTTPS 身份终结；C2 的 CI 不替代 C3a。

## 已确认问题

### 1. Medium：远端先截断再过滤，会丢失本项目的匹配记忆

- 位置：[memory.py:172](../../src/ergora/memory.py#L172)，本地后过滤位于 173–180 行。
- 场景：一个 ReMe workspace 有其他项目或非 Ergora 文件；搜索 `limit=1`，远端最靠前的命中属于其他路径，本项目的有效命中排在后面。
- 证据：请求仅发送 `query`、`limit`、`expand_links`。固定官方提交的 `SearchStep` 从请求读取 `search_filter`（上游 `reme/steps/index/search.py:256`），但本实现未传；上游在 351 行先执行 `fused[:limit]`。应用随后丢弃非本项目路径，无法取回已被截断的项目内命中。按此协议的本机 HTTP 反例中，本项目已有 `port 9000 canonical`，查询 `9000`、`limit=1` 返回 `results: []`。
- 影响：路径后过滤保护了显示内容的项目边界，但项目检索结果会受无关文件的排名影响而静默缺失。原 fixture 在 `tests/test_memory.py:65` 返回全部文件、没有执行请求中的 limit，因此未覆盖这一行为。
- 最小修复：将本项目有效记忆路径通过官方 `search_filter.paths` 传给搜索，在远端限额前约束范围；没有有效路径时直接返回空。继续保留本地路径白名单与本地正文重读。增加一个遵守 limit、外项目排名在前的 HTTP 回归。
- 判定：CONFIRMED；置信度 99。

### 2. Medium：内容不变时，轮换后的凭据配置没有保存到 mirror

- 位置：[memory.py:150](../../src/ergora/memory.py#L150)，保存 mirror binding 的 UPDATE 位于 154–155 行。
- 场景：用 `token_env=OLD_REME` 同步过记忆；在相同 endpoint 改绑为 `NEW_REME` 并执行同步，正文修订不变；随后切回 SQLite、撤销旧变量并删除这条记忆，再执行同步。
- 证据：当前绑定虽然在 141–142 行被选中，但只有正文 revision 改变才会持久化 `remote_binding`。反例中第二次同步返回 `changes_acknowledged: 0`，数据库中的 mirror 仍为 `OLD_REME`；切换 SQLite 后删除路径使用旧快照，报旧凭据变量不可用。新的有效凭据不再能由当前绑定提供。
- 影响：常规凭据轮换会留下过期的投影访问配置，后续纠错或删除传播失败；本地正文已经删除时，远端旧正文仍需额外人工恢复配置才能清理。
- 最小修复：当前 endpoint 对应的 mirror 应在绑定变化时更新访问配置，即使正文修订未变；配置更新和正文写入确认分开处理。增加“轮换变量、同步不改正文、切换 SQLite、撤旧变量、删除同步成功”的回归。
- 判定：CONFIRMED；置信度 99。

### 3. Medium：只有本地确认标记，没有重建丢失远端投影的入口

- 位置：[memory.py:150](../../src/ergora/memory.py#L150)，镜像登记使用 134 行的 `INSERT OR IGNORE`；CLI 的 sync 在 [cli.py:58](../../src/ergora/cli.py#L58) 未提供重建参数。
- 场景：恢复完整 Ergora state 到新设备，并在原 URL 启动一个空 ReMe workspace；或同一服务的投影文件丢失后需要从本地事实来源重建。
- 证据：恢复的 `memory_mirrors.revision` 仍等于有效记忆修订，`INSERT OR IGNORE` 保留该标记，revision 相等时不再发起 `/write`。本机 HTTP 反例先成功同步、清空远端文件，再同步得到 `changes_acknowledged: 0`，远端仍为空，后续搜索也持续为空。
- 影响：SQLite 中的事实完整，但用户无法通过现有同步命令恢复派生投影；必须修改每条正文、改用另一个 URL 或直接修改内部数据库。这使可选后端的恢复路径不完整。
- 最小修复：提供明确的强制重建参数，例如 `memory sync --force`，对当前 endpoint 的所有有效记忆重新写入并确认，同时保留待删除任务及失败重试语义；在接入手册说明何时使用。增加“同 URL 清空远端、强制同步重建、检索恢复”的回归。
- 判定：CONFIRMED；置信度 95。

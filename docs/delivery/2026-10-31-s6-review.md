## F1 · P2：迟到的工作流响应覆盖较新的页面状态

位置：`src/ergora/data/console/app.js:1616`（保存结果无条件替换 `workflow`）；同类入口在 `:1465`（模板载入结果），另应检查 `:1714` 的异步 JSON 载入。

独立 Chromium、安装 wheel、临时隔离项目复现了两个场景。网络拦截只延迟真实服务的响应，不伪造响应或业务状态：

1. 在大型开发模板点击“保存草稿”，等待服务端真实接受保存，然后暂缓向浏览器交付响应。在这期间修改“任务说明”，点击“更新单元草稿”。“完整任务输入 JSON”已包含新文字，证明已进入页面草稿。释放旧保存响应后，页面显示“草稿修订 1”，新文字消失。观测结果：`editPresentBeforeSaveResponse=true`，`editPresentAfterSaveResponse=false`。
2. 延迟 `repository-governance` 模板响应；随后载入 `training-optimization` 并确认“训练优化模板”已显示。释放先前响应后，模板选择器及页面又变为 `repository-governance`。观测结果：`newerTemplateBeforeOlderResponse=training-optimization`，`templateAfterOlderResponse=repository-governance`。

`refreshSequence` 只保护 dashboard 刷新，无法保护这些直接写入全局 `workflow` 的异步分支。保存和载入按钮也未阻止后续编辑/载入。请求延迟或并发时，旧响应因此夺取新页面状态的所有权；场景 1 会丢失用户已显式更新到草稿、但尚未持久保存的工作。服务端 revision 冲突检查不能恢复这些页面编辑。

最小修正：为工作流的异步载入/保存建立明确的请求和编辑身份，只有仍匹配当前项目、草稿与编辑版本的响应才能替换页面状态；保存期间也可采用完整禁用相关编辑和切换控件的方式。迟到的保存响应若对应已变化的页面，应保留新编辑，并正确处理服务端已推进的 revision，不能仅丢弃响应而让下一次保存永久使用旧 revision。模板载入应保证最新选择胜出；切换项目、打开草稿及 JSON 载入也须使旧操作失效。无需引入新的状态框架。

复审要求：在真实浏览器重跑上述两种延迟场景，确认更新后的内容可继续保存、重新载入；补查保存中切换项目/草稿及 JSON 载入。现有 `test_web.py` 不执行前端，因此其通过不能覆盖 F1。

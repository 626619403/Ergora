### 1. High：实际评分脚本可以遗漏于固定文件清单，改分后仍可采用

- 位置：[evaluation.py:57](../../src/ergora/evaluation.py#L57)，收集指纹位于 67–70 行。
- 场景：注册 `evaluator_argv=[python, /absolute/path/score.py]`、`evaluator_files=[]`；先评价 baseline，再修改 `score.py`，用同一 suite 评价候选并采用。空列表被允许；非空但漏掉评分入口时也有同一缺口。
- 证据：指纹只涵盖 `argv[0]` 和显式声明的文件，没有覆盖可直接定位的评分脚本。独立反例把评分从固定 0.2 改为固定 0.9，双方均 `succeeded`，`compare.eligible=true`，`skills.adopt` 实际成功，评分脚本未出现在 `file_sha256` 中。
- 影响：两份语义不同的评分程序产生的证据被当作同一冻结合同；这直接突破“修改评分后必须注册新 suite、重跑双方”的采用边界。文档要求维护者固定其他环境和导入依赖，不能补足已直接指定的评分入口未被固定这一缺口。
- 最小修复：自动纳入 argv 指向的现有本地入口文件，或在它未声明时拒绝注册；继续固定显式依赖和解释器。相对路径应按项目根一致解析。增加“遗漏评分入口、改脚本、旧 suite 拒绝运行/比较/采用”的回归。
- 判定：CONFIRMED；置信度 99。

### 2. High：全部 evaluator 失败仍会汇总为 GEPA 搜索成功

- 位置：[optimization.py:96](../../src/ergora/optimization.py#L96)，失败转零分位于 100–108 行，成功汇总位于 170–173 行。
- 场景：可信 evaluator 每次输出非法响应 `[]`，提案器按协议返回合法文本；用真实 GEPA、`max_evaluations=3`、`max_proposals=1` 搜索。
- 证据：独立运行保存了 3 份 `status=failed` 的 evaluation，但 optimization 返回 `status=succeeded`、`best_candidate=baseline`。Adapter 把未成功的评价转成普通零分，只有 `cancelled` 被传播；SDK 正常达到 metric-call 终止条件后，外围将仍为 running 的作业标为成功。CLI 随之返回成功退出码。
- 影响：没有一次可用评分的搜索仍被对外报告成功；baseline 也没有可信分数，后续自动消费者无法仅按作业状态区分有效搜索和评分基础设施错误。完整采用门禁仍会拒绝这些失败评价，因此本项不是直接绕过采用。
- 最小修复：保存失败 evaluation ID 后，将评分协议错误、超时、预算停止等非成功状态传播到优化作业，并终止后续调用；不要将基础设施失败等同于一份合法零分结果。若继续搜索非法候选，应把候选格式拒绝与 evaluator 故障分开处理。增加全部 evaluator 失败和 evaluator 超时的真实 GEPA 回归，断言外层不能 succeeded。
- 判定：CONFIRMED；置信度 99。

### 3. Medium：优化器累计成本超限后，同一评价批次仍继续调用

- 位置：[optimization.py:96](../../src/ergora/optimization.py#L96)，以及 [evaluation.py:155](../../src/ergora/evaluation.py#L155)。
- 场景：suite 预算 0.45，每次评分报告成本 0.1，配置 1 个 train 和 2 个 validation；提案器报告零成本。前几个批次已花费 0.4，随后候选完整 validation 批次开始。
- 证据：独立真实 GEPA 运行的批次成本为 `[0.2, 0.1, 0.1, 0.2]`，最终 0.6。最后批次第一例完成时累计已为 0.5，仍调用了第二例。`evaluate` 每批重新使用完整 0.45 限额；优化器只在整个批次返回后加总并检查累计值。
- 影响：报告中已经明确超限后，仍产生本可停止的后续工具调用。报告成本不能提供账单硬限额这一已声明边界，不影响“收到超限回执后停止后续调用”的要求。
- 最小修复：把优化作业剩余报告预算传入评价执行器，逐例累加并停止；保留实际产生的超限回执和部分证据，不改变原冻结 suite。增加已有累计成本、后续多例批次在第一例越限的回归。
- 判定：CONFIRMED；置信度 99。

### 4. Medium：脚本可执行位不参与 skill 目录身份

- 位置：[skills.py:25](../../src/ergora/skills.py#L25)。
- 场景：skill 指令调用 `./run.sh`；文件正文不变，将来源脚本从 0644 改为 0755 后重新导入，或改变已存快照脚本的可执行位。
- 证据：树摘要只包含相对路径和字节 SHA。独立反例中来源 chmod 前后返回同一 digest；已存版本脚本 chmod 后，`skills.get` 仍接受原 digest。`copytree` 会保留该属性，因此运行行为可以不同，而版本身份和证据绑定不变。
- 影响：一个真实影响脚本执行的资源变化无法成为候选，也不能被采用前的身份检查发现；后续 agent 从记录的资源目录执行脚本时，可能得到与评价不同的行为。
- 最小修复：至少将各文件的可执行属性纳入文件清单和树摘要，并继续在导入、导出、get 时保存和检查。增加“仅 chmod 形成不同候选”和“快照 chmod 后拒绝使用”的回归。
- 判定：CONFIRMED；置信度 98。

## 已核实的起点和采用方案

现有基础 State 只有 projects / agent_runs，其他 14 表由七个领域模块 lazy 创建；总计 16 表、`PRAGMA user_version=0`，结构和合成数据已由 A2 固定。继续采用标准库 sqlite3、原表名/文档/查询与各领域事务，不加入 ORM 或万能 JSON repository。

R3.1 在存储边界串行初始化，迁移使用显式事务，不用会隐式提交的 executescript。迁移前从单独只读连接调用 SQLite backup，保存原库版本；任何 DDL / 版本提交失败均回滚。初始化锁与 SQLite 写锁各负责新客户端串行化和数据库事务，连接每次核对支持版本。已有表结构不符合旧格式时明确拒绝，未知额外表/索引/触发器须保留，不静默重建或丢弃。

旧 0.2.0 没有版本检查，仅 user_version 无法隔离它。拟给已知表的 INSERT / UPDATE / DELETE 增加触发器，要求连接注册的 writer-schema 函数匹配版本；旧连接缺少此函数，其写操作会在 SQLite 拒绝，新连接注册当前版本。此保护针对旧二进制的已知数据库写路径，不是同用户恶意 SQL 的安全边界，也不能停止旧进程写文件或启动外部工作。升级前应停服务并对账在途工作。

隔离 SQLite 原型已实际确认：迁移前已打开的旧连接也会在三类 DML 被拒绝，新连接可以写、旧读取保留；另一个只读连接能在迁移连接 BEGIN IMMEDIATE 持有锁时完成 backup，随后 DDL / user_version 回滚保留旧值。原型只在忽略的检查目录，无实际用户库改动；最终产品仍须回归和真实两 OS CI。

R3.2 采用明确的离线备份，记录原 home、数据库版本和文件内容/执行位清单，恢复前核对；不宣称 SQLite 的一致快照自动覆盖文件、外部业务仓库、reference / Temporal 服务或 ReMe。恢复不默默修改持久文档中的绝对路径或重新计算旧证据；跨目录/机器迁移需明确支持边界。自动迁移 DB 快照与完整资产备份要清楚区分。

## 必须保留的边界

- 原项目、草稿、记忆、Skill 的修订冲突检查和领域 SQL 事务不迁入通用接口。
- 原摘要、Skill 文件/执行位、评价可信文件、候选身份和 unknown / cancelled 等状态保持；不通过重写旧 JSON 完成迁移。
- ReMe 仍是可重建投影，重建不修改本地 canonical 记忆和修订。
- 升级/恢复必须说明停旧服务、保留备份、核对原位置和再启动；回退不是单纯 git revert。
- 每个子节点要包含新库、旧库、重复启动、故障回滚、新版本拒绝、跨进程及真实 Windows 验收；按受影响范围分配检查，不重复声称所有节点都已通过。

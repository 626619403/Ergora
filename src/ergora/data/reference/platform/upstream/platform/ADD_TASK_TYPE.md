# 新任务、新类型与新执行引擎

## 可移植入口

v1.3 新任务优先使用 `portable/examples/<type>/task.json`，项目策略与工单绑定分别维护。按 [PORTABILITY.md](PORTABILITY.md) 编译；按 [A2A.md](A2A.md) 远程委托，或显式导出 v2 请求走旧 Symphony 路径。当前编译器支持既有两类开发流程；新增运行时必须实现并验证适配器，不只是更改 binding 中的名字。

## 新增同类型任务

复制对应 `task-types/<type>/examples/request.json`，生成一个新的 `task_id`，填写真实 tracker、基准和起始提交、目标、允许路径、验收、约束和工作单元。保留正确的 `task_version` 与 `profile_sha256`，通过平台验证后交接。无需复制服务、另建 agent 团队或修改技能注册。

同一任务 ID 对应不可变输入。目标、计划契约、基准、写入范围或工作单元发生实质变更时，结束/隔离旧任务并创建新修订 ID。不要原地修改已提交 JSON，也不要用重命名文件绕过正在运行的任务。

## 新增任务类型

只有阶段语义、必需证据或权限边界不同，才新增类型。只改变目标、仓库、语言、模型或相关 skill，通常仍然是现有类型的实例。

1. 写清输入、输出、失败条件和完成定义；列出需要人的决定。
2. 编写受信 profile：阶段角色、检查 ID、必需产物、单元数量及并发/超时上限。
3. 提供 instructions、JSON Schema、有效与无效示例，并补充语义验证。Schema 验证不能代替 DAG、路径范围和证据关系检查。
4. 更新平台的受信注册表和 Symphony 项目 `enabled_task_types` 允许列表；由平台维护者审查、测试、发布。此版本的注册表是显式允许列表，复制一个目录不会自动启用类型。
5. 接执行器映射：每个阶段对应什么受控 agent 任务或 CI 检查、用什么凭据、如何隔离与取消。不得加载候选仓库提供的任意 Python 插件或 shell 字符串。
6. 验证正常执行、缺证据、错误提交、越权路径、循环依赖、过期批准、重复提交、worker 重启和取消未确认，再在一个项目试点。

同样采用 inventory → plan → approval → work DAG → integrate → verify → review 的类型，应继续复用共享 `DevelopmentWorkflow`。出现不同的持久状态或副作用语义时，才考虑新增引擎；例如既有训练实验走独立的训练工作流。

## 版本与兼容

将 profile 与代码作为不可变发布一起部署。不要编辑正在执行任务使用的 profile 来“修复”任务；摘要变化会使旧请求被拒绝。变更规则时发布新的明确版本并保留旧版本处理存量任务，然后迁移新任务。当前内置两个类型的版本为 1；新增版本需要同步扩展注册表与验证器。

修改已部署 Temporal workflow 的控制流，还需采用 Temporal 的版本化/兼容部署机制并测试历史重放；仅提升 `task_version` 不能替代工作流兼容性处理。不要滚动覆盖存量运行依赖的 worker 代码。

## 项目差异放在哪里

| 内容 | 所属层 |
| --- | --- |
| Issue 平台、项目路径、服务目录、密钥、Temporal namespace | 项目部署配置 |
| 开发/检查命令、模块映射、语言分析器、可信基线 | 受保护的项目策略与执行器 |
| 工作阶段、必需证据、角色和并发上限 | 受信任务类型 profile |
| 本次目标、路径、验收、DAG、基准提交 | 不可变任务实例 |
| 领域材料、辅助工具用法、相关技能 | 按阶段加载的上下文；不能覆盖上面的权限与检查 |

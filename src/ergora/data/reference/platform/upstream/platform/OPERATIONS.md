# 交付与运行约定

## 最小服务划分

| 组件 | 职责 | 部署边界 |
| --- | --- | --- |
| Symphony / Codex | 领取工单、准备需求和起始提交、交接请求 | 模型访问、限定项目 tracker/Git 身份、隔离工作区 |
| 持久 bridge | 准入、去重、启动或找回 workflow、同步工单标签 | 独立服务；持久本地 SQLite；Temporal 和 tracker 身份 |
| Temporal Cloud + 开发 worker | 阶段状态、DAG、等待审批、结果汇总 | 云端 CPU worker；无本地模型；服务端由 Cloud 托管 |
| 可信执行器 | 消费阶段请求，运行角色/检查，保存证据与真实身份 | 团队 CI/任务系统；隔离 worktree、容器、数据与资源 |
| 人工入口 | 批准计划、决定例外、审阅最终候选和合并 | 团队已有身份系统/受保护 CI；不向编码 agent 暴露审批写权限 |

本包的文件适配器是**可运行的阶段交接协议**，不是已经接好的 Codex/CI 执行服务。平台发出请求；你的受信执行器消费请求并回传证据。模型会话不能自己向可信目录写 PASS。

## 多人使用与隔离

初期按项目部署一组配置、专用目录和最小权限身份。共享套件代码，隔离运行数据；不同项目不能复用 task ID 空间或互读审批。团队成员通过受控入口提交任务，由项目允许列表选择类型。

不要把单机原型当成多租户 SaaS：SQLite/flock 仅支持单协调主机的持久本地盘，不能部署多个 bridge 共写 NFS。跨主机 HA 需要事务存储、租约与身份网关等进一步实现。不同进程或环境变量清理不构成安全隔离；采用独立 Unix 用户/容器、挂载 ACL、服务身份和网络边界。文件适配器目录也必须与候选仓库分离。

每个工作单元一个隔离工作区。执行器在触发外部动作前核对 task fence、job ID、允许路径、依赖输入及项目身份；幂等键是平台发出的 job ID。并行前给运行时端口、数据库、测试账户和临时对象命名空间分配独立资源，限制并发和 walltime。相同模型也可以担任不同角色，但不能共享可写状态与审批权限。

## 计划与审查

人批准当前计划版本一次。范围、契约、基准或计划变化时，新修订重新批准；无需逐个批准普通的受限实现步骤。计划批准允许开始实施，不能代替最终合并审阅。高风险外部动作仍由独立部署流程负责。

verify 阶段从可信项目配置选择检查，核验完整最终候选；review 使用独立身份和新会话读取最终差异与证据。仅换一个角色名称不能证明独立。SHA/hash 证明内容绑定，身份由部署 ACL 和可信执行器负责；它们不证明测试本身充分，也不保证所有代码正确。

最终 `REVIEW_READY` 表示候选可以提交给人审阅。合并前由受保护分支/合并队列确认目标分支未漂移，必要时在新的集成候选上重跑检查。此包没有自动合并、部署或执行生产迁移。

## 故障处理

| 现象 | 操作 |
| --- | --- |
| 缺少审批、执行器或证据 | 保持等待/阻塞，修复接入条件；不得造回执 |
| 提交响应丢失 | 查持久 ledger 与原 workflow；禁止直接启动同一任务的新副本 |
| 原始请求/profile 不匹配 | 按版本冲突处理；结束旧修订并创建新任务 |
| 单元失败 | 不启动它的下游；保留日志和候选，不悄悄跳过检查 |
| 审查要求改动 | 新任务修订包含修改目标；新候选重新验证，不复用旧 PASS |
| 取消或超时 | 发布 fence；执行器停止新动作并核对已有作业；未确认停止的作业必须人工协调 |
| 基准/策略改变 | 尚未开始的请求重新规划；合并前再次核验目标分支和策略 |

文件 fence 不是操作系统 kill，也不证明远端作业已经停止。执行器必须实现取消和独立 walltime；未确认的任务保留为待协调，不能释放同一资源给竞争任务。重启后先读取持久状态，绝不靠聊天记忆猜测进度。

### 取消未确认后的人工恢复

`CANCEL_UNCONFIRMED` 或 `NEEDS_RECONCILIATION` 继续占有工单；不会因为工作流终止就允许新一轮改写。受信操作员先在执行平台核实所有外部作业已结束、旧请求已被 fence，再准备 `cleanup.json`，从 `symphony/` 目录执行：

```bash
python bridge.py --config /etc/agent-pipeline.json reconcile PROJECT-ISSUE-r1 cleanup.json
```

恢复证据必须包含 `schema_version: 1`、`task_id`、`issue_id`、`request_sha256`、`workflow_id`、`run_id`、`all_external_work_stopped: true`、`operator`、`evidence_sha256`、无凭据 HTTPS `evidence_uri` 和 24 小时内的 `confirmed_at` Unix 时间。所有绑定字段取自真实 bridge 收据/ledger；这里的 `request_sha256` 是 **outbox 请求原始字节**的摘要，不是 task spec 中规范化请求的摘要。

此命令验证恢复声明与运行绑定，不替你停止外部任务，也不认证 JSON 中的操作者名字。必须通过受控操作员身份执行，先检查证据再确认；不能让编码 agent 调用它解除自己的阻塞。只有 `safe_to_rework` 成立后，负责人才重新放行新任务修订。

## 给人的状态页

每个任务只展示：目标/类型、当前阶段与下一步、最终或当前候选、证据与覆盖范围、阻塞/遗留问题、需要人的决定。长日志、完整轨迹、扫描报告和过程讨论只链接，不塞进每个 agent 的上下文。

每次失败留一条可复用记录：触发条件、检测方式、根因、修复与新增规则。反复出现的审查意见优先转成明确的检查器。治理扫描可定期产生小任务，但上线前先选择负责人、频率、配额和审核方式；本交付没有创建任何定时任务。

## 发布前验收

- 在一个低风险仓库真实跑通从 issue 到 `REVIEW_READY`；对照最终 SHA 和原始检查记录。
- 制造重复提交、响应丢失、重启、越界文件、缺证据和旧审批，确认均被正确处理。
- 验证执行器不会重复启动同一 job，也不会运行 fenced 任务；确认 walltime 和取消行为。
- 验证编码 agent 无法写审批、回执、可信检查策略或平台安装目录。
- 验证独立 reviewer 身份来自可信执行器，合并队列不会采用过时证据。


## v1.3 多入口与可移植任务

- Symphony 与 A2A 共用 `dev_platform.runtime.DevelopmentTransport`，原始 Temporal 输入和 run 绑定的核验逻辑只维护一处。
- 开启第二入口前按 [MIGRATION.md](MIGRATION.md) 排空旧活动记录；两个入口使用同一 [共享所有权库](INGRESS.md)。不要删除数据库、改目录或绕过入口直接启动工作流来解除阻塞。
- 普通 agent 只持有自身 A2A 调用凭据，不持有 Temporal 管理密钥、准入数据库写权限、共享所有权库或审批目录权限。
- A2A completed 仅表示任务范围内的候选交付；没有合并权限。取消未确认按 [A2A.md](A2A.md) 的可信清理流程处理。
- `compiled.json` 固定任务、模板、项目 policy 和 binding。新策略用于新的准入；最终合并前仍需针对当前目标分支及现行策略重新核验。

# 大型变更模板

适用：跨模块功能、公共 API 演进、平台替换或需要多工作单元协作的重构。每个任务仍应有一个可验证的交付目标；长项目拆成多个任务，每个任务重新固定输入、基准和批准范围。

## 提交前填写

1. 固定基准提交、目标、允许路径、兼容性要求及验收条件；禁止改路径由可信模板和平台策略定义。
2. 明确公共契约、持久化格式和部署顺序。未知项先设为调查任务，不让实施 agent 猜测。
3. 把工作拆成有向无环图。每个单元填写唯一 ID、依赖、路径所有权、交付物和完成条件。仅并行执行依赖已完成、写入范围不冲突的单元。
4. 规划唯一集成人、候选构建方式、版本兼容矩阵、迁移演练与回滚条件。变更中不允许修改批准它的可信策略。

## 阶段与交付

| 阶段 | Agent 任务 | 必须交付 |
| --- | --- | --- |
| inventory | 梳理受影响业务流、消费者、存储、接口和部署依赖 | 影响地图、行为基线、未知项 |
| plan | 定义契约、替换边界、DAG、测试与迁移方案 | 执行计划、契约版本、单元所有权、发布/回滚方案 |
| approval | 人审范围、公共契约及不可逆决策 | 绑定具体计划版本的可信批准记录 |
| work units | 根据固定契约在独立工作区实现 | 单元提交、单元测试、契约兼容结果 |
| integrate | 按依赖顺序合成，处理共享文件与冲突 | 唯一候选提交、来源清单、冲突决策 |
| verify | 在最终候选上跑跨模块验证 | 兼容、端到端、迁移演练及回滚证据 |
| review | 新上下文独立审接口、边界和运行风险 | 审查结论、交付摘要、明确的未决项 |

## 多 agent 协作纪律

- 一个工作单元一个隔离工作区、一个写入责任人。角色名称、模型不同或聊天窗口不同都不等于环境隔离。
- 共享契约先固定，再并行。契约变更必须使受影响计划和验证证据失效，并提交新任务修订；不要让两个 agent 各自猜接口。
- 父任务只接收结构化摘要、提交和证据链接。实施日志保存在可查询附件；避免把完整聊天不断复制到每个 agent。
- 独立工作单元可以并行；有依赖的单元必须等待其上游成功。任一单元失败时，不把它的下游当作可运行任务。
- 集成人生成新的候选后，重新跑该候选的相关检查；各单元的成功不能代替集成验证。
- 对数据库或持久化格式，优先兼容式分阶段迁移。不可逆操作另设部署流程和人工批准，本开发模板不执行生产迁移。
- 依赖升级、功能变更和全仓格式化尽量分开交付；不要让无关 diff 掩盖接口与数据风险。

## 完成条件

批准计划与当前输入一致；全部工作单元及其依赖成功；最终候选通过所需检查（包含实际 Git diff 的允许与禁止路径核验）并经过独立审查；兼容性与回滚约束明确；交付摘要能让人快速确认目标、影响面、证据和剩余风险。最终产物是待审阅的集成候选，不是自动上线。

示例请求见 `examples/request.json`；字段以 `input.schema.json` 和平台验证器为准。模板共享执行引擎，新增任务类型不需要复制调度服务。

## 参考与适配

[OpenAI Harness engineering](https://openai.com/index/harness-engineering/) 提供了版本化执行计划、可观测隔离环境和架构约束的实践背景。本模板的 DAG、证据绑定与人工决策点是为既有仓库、多用户使用及高影响变更设计的约束。

# 仓库治理模板

适用：给已存在的仓库建立可追踪的规则与知识入口，修复范围明确的结构、重复实现、依赖边界或文档漂移问题。每个任务只处理一个可独立验收的问题；跨多个子系统或改变公共契约，改用 `large-change`。

## 提交前填写

1. 固定基准提交，并填写目标、可改路径及验收条件；禁止改路径由可信模板和平台策略定义。
2. 先把现状登记成可复跑的检查结果。旧测试失败、历史架构违规和待处理文档必须有稳定标识；不能把扫描当天的失败重新当成“允许基线”。
3. 将实施拆成小工作单元。公共工具、依赖文件、生成入口只能有一个写入负责人；需要共改同一文件的工作单元按依赖顺序执行。
4. 指定谁批准计划、谁核验 CI 证据、谁负责独立审查。平台角色名不是账号认证，部署层必须验证真实身份。

## 阶段与交付

| 阶段 | Agent 任务 | 必须交付 |
| --- | --- | --- |
| inventory | 只读识别模块、入口、所有者、测试与历史失败 | 仓库地图、可复现基线、按影响排序的问题清单 |
| plan | 选一个问题，限定范围，设计回滚与检查 | 执行计划、路径所有权、验收条件与风险 |
| approval | 人确认范围与行为契约 | 绑定计划版本的可信批准记录 |
| work units | 在隔离工作区小步实现，记录新规则 | 单元提交、测试与修改说明 |
| integrate | 合成唯一候选提交 | 候选提交与工作单元来源 |
| verify | 从可信检查配置运行新旧对比 | 完整检查结果、违规增减与影响证据 |
| review | 新上下文独立核对需求、代码与证据 | 审查结论、遗留问题与交付摘要 |

## 旧仓库的默认纪律

- 先表征行为，再改结构。没有足够测试时，优先为受影响接口补契约或表征测试；不要一次性制造全仓测试工程。
- 旧问题可以登记为历史债务，但新违规不可抵消旧违规数量而“净通过”。用具体违规指纹比较，修复后删除旧豁免；新增豁免需要单独审查。
- 对公共契约的改变、数据迁移、CI 权限调整和扩大写入范围，停止当前实施并重新规划。不要把它藏在“清理”提交里。
- 文档地图短而可导航。`AGENTS.md` 指向架构、命令、计划和质量规则；详细说明各有所有者、最近核验提交及对应的检查。
- 规则要能被检查。把反复出现的审查意见改成检查器或测试；检查失败消息给出文件位置、违反规则与可行修复方向。
- 持续治理以独立小任务运行。扫描可产生待办与修复候选，不自动跨任务改写基线、降低门禁或合并代码。

## 完成条件

可信 CI 针对**同一最终候选提交**核对实际 Git diff 的允许与禁止路径，并产生所需证据；未解决的新增违规为零；审查者与实施者隔离；变更、行为影响、旧问题、回滚和后续任务可在一页交付摘要中查看。最终状态表示“可供人工合并审阅”，并不执行合并或部署。

示例请求见 `examples/request.json`；字段以 `input.schema.json` 和平台验证器为准。模板使用共享执行引擎，不加载仓库内任意 Python 插件。

## 参考与适配

[OpenAI Harness engineering](https://openai.com/index/harness-engineering/) 是知识导航、可执行约束与持续小步治理的参考。本文的审批、基线比较和隔离规则是面向多人既有仓库的实现选择；不假定该文章中的自主合并经验适用于所有仓库。

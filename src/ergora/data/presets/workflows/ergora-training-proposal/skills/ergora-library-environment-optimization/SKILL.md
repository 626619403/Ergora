# Framework, library and environment candidates

Apply this policy during framework setup, baseline construction, source-flow analysis, experiment design, profiling proposals, kernel assessment and measurement review. Read the original task and current stage to identify permitted changes and fixed algorithm, model, structure, size, precision, data, update and quality semantics. For a first round that fixes model algorithm/structure/size/precision, keep those fixed while exploring compatible implementations. Later numerical or quantization work follows its own explicit task scope; a library's available modes or defaults do not expand it.

## Select an implementation

Map required behavior, dependencies and possible redundant computation/storage first, then choose a bounded intervention from evidence. Code edits, alternative libraries, backends and framework replacements are candidate paths from the initial setup and baseline stages onward. Agents choose tools and methods suited to the target stack and an observed bottleneck, setup/compatibility need or explicitly unmeasured hypothesis; distinguish hypotheses from measurements. No package is mandatory. DeepEP and TransformerEngine are examples, not selected dependencies or authorization to change precision. A compatible communication, fused or backend implementation can preserve the original numerical contract.

Identify the actual target component seam and preserve its tensor/data, gradient, normalization, collective, parameter/state and checkpoint/restore obligations. Report why an alternative addresses the observed question, its expected tradeoffs and the smallest discriminating check. Preserve the flow-first diagnosis and retained kernel assessment, including a valid no-kernel-change conclusion. Tool presence, supported operation, compatibility, successful invocation and measured gain are separate observations; mark unavailable/unsupported operations visibly and retain their errors or missing evidence.

## Adapt the task environment

Readonly proposal leaves select or plan the candidate and supply the required execution handoff; their grants do not acquire shell, network or installation capability. The actual execution/build owner may adapt or upgrade the authorized task environment and install suitable libraries under the user's existing authorization, without asking for the same permission again. Use only supported tools and the task's existing resource, attempt, clock, budget and stop/recovery boundaries. A proposal, installed package or environment change does not grant adoption or broader access.

Before adaptation, retain the reproducible original baseline, source/configuration and environment as distinct immutable identities. Prefer a separate candidate environment or retain a restorable original snapshot and verified rollback route. Keep original runs and references readable; environment changes do not automatically rebaseline, overwrite evidence or reset clocks. Existing valid baseline reuse remains subject to the original comparison policy; this recipe adds no mandatory full-baseline rerun or new quality tier.

For every dependency or environment candidate, complete the supplied **environment-change record** context. The proposal records planned operations, owner, compatibility checks and rollback; the execution owner appends actual commands, versions/build identities, results and failures to the same candidate-bound record. Preserve unsuccessful builds, compatibility errors and rollback outcomes. Record unknown facts as unknown rather than filling them from a package's advertised support. Runtime artifacts stay in the target project's original artifact store; public documents and prompts use sanitized references, with secrets retained only through the original environment-reference policy.

## Native harness preflight and failure reporting

Apply these checks at the target's actual harness, DataLoader and stream construction seams, under the original execution owner's grants. Record the exact source/candidate, Python and framework builds, OS/container, multiprocessing start method, node/rank/worker set, tensor-sharing strategy and cache/temp configuration. Package metadata, a standalone control and a matched target-harness regression are separate evidence; report unavailable operations and remaining target differences explicitly.

- **Host capacity.** Use an explicit process-set capacity ledger, not summed rank RSS as physical host usage or admission proof. Fork-shared pages appear in multiple processes' RSS. Record proportional/shared-page accounting and process coverage separately from host/cgroup availability and anonymous versus file-backed/cache attribution, with units, sampling windows and original reader identities. Missing or inaccessible counters remain UNKNOWN with their availability/error; never substitute zero. Guard thresholds belong to the actual task/resources and metric semantics.
- **Task-local paths and IPC.** Allocate short, task-owned cache/temp namespaces from collision-resistant digests of the original task/attempt/node/rank identity; keep complete provenance in the record rather than expanding long run names into paths. Create exclusively and handle an occupied path without reusing an unknown owner's directory. Bind per-task/rank environment before multiprocessing or tempfile consumers cache paths; preserve global HOME/temp settings. Check the fully derived listener/socket pathname in the target filesystem encoding, including every runtime-added component and platform terminator rule, against the actual platform limit. A short TMPDIR alone is not that check. Keep the owned directories alive until original worker/listener cleanup is confirmed, then remove only that scope through its original cleanup owner.
- **Optional streams and replay.** Select an optional replay/stream with `value if value is not None else fallback`. Preserve valid empty, non-sized and infinite objects; avoid truthiness, `or`, length or length-hint probes for selection unless the object's contract explicitly defines emptiness. Real iteration retains the original finite step/stop budget and data contract.
- **Primary failures.** Preserve the original exception, traceback, process status/exit outcome and cancellation/STOP identity before secondary diagnostics. Telemetry is best-effort, time/output bounded under the remaining original budget, with its own errors recorded separately. It must neither replace or hide the primary failure nor bypass original cleanup/cancellation, swallow STOP or turn unknown cleanup into success.

A pathname-length check cannot certify Tensor transport. Require a regression through the target's actual existing harness/DataLoader constructor with matched Python/framework build, multiprocessing start/rank/worker/temp/sharing settings: transfer and verify real Tensor batches through the applicable file-descriptor/resource-sharer/SocketListener path, observe the actual derived address and confirm original owned worker/listener cleanup. Record when that branch or runtime is unsupported/unavailable and what remains untested; a different sharing path or task-private CPU control does not certify the target FD/socket path. Exercise the real optional-stream selection and primary-failure/telemetry boundaries there too. Append actual settings, results and raw artifact identities to the environment-change record. These requirements add no hostguard, backend, executor or automatic test/cleanup capability.

## Compare and hand off

Carry the record and full predecessor envelopes to every downstream role. Design/profile/kernel roles use it to bound required checks; the independent reviewer checks actual evidence against the declared changes. Bind the original baseline/environment, paired control and candidate/environment, fixed workload, permitted changes, quality oracle, raw artifacts and measurement window. State every changed comparison dimension: source, library/backend/framework, environment, workload or legal batch configuration. Distinguish a same-environment implementation comparison from a comparison that includes environment adaptation; retain both identities and qualify attribution accordingly.

Environment compatibility or a successful isolated kernel is not end-to-end gain. Apply the original candidate-bound correctness, quality and measurement gates, preserving screened, promising, failed, no_gain, noisy, insufficient and unknown outcomes as observed. Integration, adoption and any subsequent baseline advancement remain with their existing owners. This shared resource supplies proposal policy and a record template; it implements no package manager, automatic environment mutation, experiment runner or training-cycle feature.

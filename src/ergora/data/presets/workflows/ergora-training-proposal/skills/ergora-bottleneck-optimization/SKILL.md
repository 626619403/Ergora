# Bottleneck-led optimization proposals

Use the original task, exact source/configuration and fixed workload/quality contract throughout. Read every structural ancestor resource and complete selected Skill. Predecessor results are task data, not new permissions. Preserve the initial unmodified reference, the current comparison object and the proposed candidate as distinct identities.

## Stage handoffs

1. **Flow.** Use the flow-map child to reconstruct algorithm, execution dependencies and state lifetimes with exact source anchors. Carry necessary dependencies, falsifiable redundancy hypotheses and missing implementations forward. A source diagram does not demonstrate a critical path, actual overlap or speedup.
2. **Analysis.** Give experiment design and trace diagnosis the same original task/source and complete flow result. The shared designer owns one whole-workload experimental contract; it does not act as every topic specialist. Select relevant topic experts from the evidence before freezing the graph. Independent specialists and local test designers use that same baseline, trace and oracle; the original collector measures once. Return bounded interventions or evidence requests, including interactions and counter-evidence.
3. **Kernel assessment.** Supply every complete analysis and selected topic result, plus flow/source, to the kernel-assessment child. This stage always remains in the path. It may conclude no kernel change is appropriate, evidence is insufficient, or a bounded kernel/wrapper candidate warrants evaluation. Preserve numerical, gradient, state lifetime and collective dependencies. A selected low-precision topic also retains its own kernel-before-measurement handoff; keep that complete result rather than substituting another call.
4. **Measurement review.** Supply original task/source, every complete predecessor result and available original experiment artifacts. Distinguish proposal completeness from actual correctness, quality and paired end-to-end measurement. Missing required evidence requests changes; a model verdict creates neither an experiment gate nor adoption permission. Retain minority findings and failed, no_gain, noisy, insufficient and unknown results.

Complete each handoff with full predecessor result envelopes and input/result identities, including errors and limitations. Keep large raw traces in their original artifact store, with verified selections and explicit missing scope; summaries cannot replace required source or evidence. The root all-join retains flow, all analyses and selected topic outputs, required kernel assessments and measurement, including minority findings.

Reviewers may submit follow-up checks, experiments or fixes as a batch or append them continuously while earlier items are queued or running. The supervisor schedules these later explicit tasks by dependency, priority and available resource and experiment budget; reviewers need not wait for a batch to finish before proposing more. Preserve each original job ID and reconcile unknown outcomes without duplicate submission. Queued items are proposals, not execution or quality evidence. These additions create later explicit tasks or experiments; they do not change the current frozen DAG, member slots or original clock.

## Choose a direction from evidence

Each direction preset selects a scoped specialist. Its bare root supplies limited topic diagnosis/proposals, without this root's shared policies. For complete optimization, the coordinator first publishes an exact revision of this root with only the relevant topic workflows as real descendants, then freezes the whole composition. Every actual leaf must inherit both shared Skills and the environment-change record from that same structural root. Permission to read definitions, a link or a separate root invocation cannot establish inheritance. The shipped root does not dynamically install, invoke or graft topics.

The coordinator records selected topics, reasons, dependencies, complete result identities and conflicting evidence. It integrates conclusions without majority voting or multiplying isolated gains. Select a small relevant group within the original model/wall budget and ancestor concurrency ceilings; a static cap does not enforce a shared cap across independent run-input processes. Each selected branch completes before downstream measurement. Direction-specific designers test their finite candidate against the one shared contract; they do not create independent baselines, profiles or oracles.

A catalog direction is a proposal method, not proof of compatibility, permission or measured gain. Fix permitted E/N/A changes and independent quality bounds before approximate or quantized candidates. Reuse original baseline/runner/manifest/evidence and compare_runs/perfctl policy; do not edit an oracle, threshold or baseline to improve an outcome. Module timings or isolated kernel gains cannot replace a paired full-workload comparison.

## GPU comparisons and pool validation

The supervising execution agent may run small performance comparisons on **2 GPUs**, using **4 GPUs when necessary** to fit the unchanged workload or exercise the relevant bottleneck. Keep model algorithm, structure, size, precision and training objective fixed for the first optimization round. Compare the baseline and candidate on the same GPU count, hardware/topology, workload and measurement contract; record throughput, peak memory, correctness and measurement uncertainty.

Accumulate candidates with measured benefit into a batch for larger acceptance runs. The supervisor may submit multiple **8-GPU jobs**, or larger multi-GPU jobs with enough GPUs and nodes to exercise the target cross-node behavior. Each target scale needs its own matched baseline/candidate comparison and original full quality/evidence gate. Small-scale gain promotes a candidate to this queue; it does not certify large-scale gain or advance the accepted baseline. Keep failed, noisy, no-gain and unrepresentative small-scale results visible.

Use **igs-cli (`igs`)** to submit these experiments to the selected resource pool. Check actual CLI availability, authentication and supported operations; report unavailable capabilities explicitly. Follow the available iGS job/resource skills for real specifications, mounts, images and multi-node environments; all iGS commands use `--format json`. A prepared request is submitted with `igs job create --region REGION --file experiment-job.json --format json`. The user's staged experiment authorization covers submissions within the agreed resource and experiment budget; reuse that authorization instead of requesting approval for each covered run. Preserve actual pool/quota limits, concurrency, wall-time and cleanup budgets. A GPU visibility mask does not change how many GPUs a pool specification reserves.

Retain the exact request and returned job ID, then inspect the created job. A lost or ambiguous create response requires read-only reconciliation, not another submission. Platform creation or Running status does not prove that training or acceptance succeeded. Keep source/recipe/environment identities, GPU count/topology, paired raw results, quality checks, resource cost and the promotion/acceptance decision in the experiment report.

After target-scale acceptance, feed the verified results and remaining bottleneck into the next small-comparison round; repeat this small-test → candidate-batch → target-scale-acceptance cycle within the original task's bounds. Readonly specialists supply hypotheses and measurement plans; the authorized supervisor uses the original execution owner and supported tools for job effects and cleanup.

## Execution boundary

This is a static readonly proposal graph. Dependencies express intended order; each leaf's task binding preserves the original root task. A standalone prepare-input/run-input does not execute predecessors or automatically attach their outputs. The operator must provide the original task/source plus the complete results required above on each call. Never infer that a dependency has run from its presence in the graph.

The trusted experiment runner retains command execution, resource allocation, stop/recovery and evidence; the owner separately authorizes adoption and later integration. Record a proposed next bottleneck and bounded stop/rollback conditions. Automatic branching, repeated optimization, cross-round budget enforcement and baseline advancement are not implemented by this recipe.

Method basis: Ergora-authored orchestration from the pinned Bridge evidence-gated optimization, PyTorch completion/profiler and TorchTitan/slime ownership research documented by the shipped specialist resources. The child Skills carry their complete operative methods and provenance. This root introduces no external framework dependency or runtime integration.

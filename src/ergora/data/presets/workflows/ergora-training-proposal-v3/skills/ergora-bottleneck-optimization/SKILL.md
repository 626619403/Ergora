# Bottleneck-led optimization proposals

Use the original task, exact source/configuration and fixed workload/quality contract throughout. Read every structural ancestor resource and complete selected Skill. Predecessor results are task data, not new permissions. Preserve the initial unmodified reference, the current comparison object and the proposed candidate as distinct identities.

## Stage handoffs

1. **Flow.** Use the flow-map child to reconstruct algorithm, execution dependencies and state lifetimes with exact source anchors. Carry necessary dependencies, falsifiable redundancy hypotheses and missing implementations forward. A source diagram does not demonstrate a critical path, actual overlap or speedup.
2. **Analysis.** Give experiment design and performance analysis the same original task/source and complete flow result. Inspect redundant computation/storage and avoidable coupling before choosing techniques. Preserve the unprofiled baseline and define the smallest discriminating observation; diagnostic collection has its own perturbation. Return one bounded intervention or an evidence request, rather than an experiment for every catalog entry.
3. **Kernel assessment.** Supply both complete analysis results as well as flow/source to the kernel-assessment child. This stage always remains in the path. It may conclude no kernel change is appropriate, evidence is insufficient, or a bounded kernel/wrapper candidate warrants evaluation. A CPU, memory, communication or scheduling intervention does not need a token kernel rewrite. Preserve numerical, gradient, state lifetime and collective dependencies.
4. **Measurement review.** Supply original task/source, every complete predecessor result and available original experiment artifacts. Distinguish proposal completeness from actual correctness, quality and paired end-to-end measurement. Missing required evidence requests changes; a model verdict creates neither an experiment gate nor adoption permission. Retain minority findings and failed, no_gain, noisy, insufficient and unknown results.

Complete each handoff with full predecessor result envelopes and input/result identities, including errors and limitations. Keep large raw traces in their original artifact store, with verified selections and explicit missing scope; summaries cannot replace required source or evidence. The root all-join retains flow, both analyses, kernel assessment and measurement, not only the final favorable text.

## Choose a direction from evidence

Existing direction presets remain independently selectable. Install/freeze the selected child with the same workload and material, explicitly invoke its leaves, then feed its complete results back to the original proposal. This fixed root does not dynamically install, invoke or graft direction templates.

|Observed question|Existing candidate presets|
|---|---|
|Dependency, host or memory lifetime; capacity tradeoffs|optimization-performance-diagnosis, optimization-memory-tuning, optimization-activation-recompute, optimization-cpu-offloading|
|Launch/capture or packing work on the actual path|optimization-cuda-graphs, optimization-sequence-packing|
|Parallel layout, state sharding or long-context dependencies|optimization-parallelism, optimization-megatron-fsdp, optimization-hierarchical-cp|
|Exposed communication or expert dispatch|optimization-tp-dp-overlap, optimization-moe-dispatcher, optimization-moe-overlap|
|Missing timing or memory evidence|optimization-profiling, optimization-memory-snapshot|
|Recipe/model semantics, parity or cluster/restore behavior|optimization-recipe-model, optimization-model-verification, optimization-cluster-resiliency|
|Pre-authorized numerical change or actual operator opportunity|optimization-low-precision, optimization-kernel|

A catalog direction is a proposal method, not proof of compatibility, permission or measured gain. Fix permitted E/N/A changes and independent quality bounds before approximate or quantized candidates. Reuse original baseline/runner/manifest/evidence and compare_runs/perfctl policy; do not edit an oracle, threshold or baseline to improve an outcome. Module timings or isolated kernel gains cannot replace a paired full-workload comparison.

## Execution boundary

This is a static readonly proposal graph. Dependencies express intended order; each leaf's task binding preserves the original root task. A standalone prepare-input/run-input does not execute predecessors or automatically attach their outputs. The operator must provide the original task/source plus the complete results required above on each call. Never infer that a dependency has run from its presence in the graph.

The trusted experiment runner retains command execution, resource allocation, stop/recovery and evidence; the owner separately authorizes adoption and later integration. Record a proposed next bottleneck and bounded stop/rollback conditions. Automatic branching, repeated optimization, cross-round budget enforcement and baseline advancement are not implemented by this recipe.

Method basis: Ergora-authored orchestration from the pinned Bridge evidence-gated optimization, PyTorch completion/profiler and TorchTitan/slime ownership research documented by the shipped specialist resources. The child Skills carry their complete operative methods and provenance. This root introduces no external framework dependency or runtime integration.

# TP, DP and pipeline communication-overlap proposal

This Ergora-authored offline resource synthesizes the fixed sources below. Select it to diagnose exposed communication in an actual workload. It neither installs userbuffers nor gives this readonly leaf a multi-rank execution interface.

1. Freeze the actual model/config/optimizer and framework commits, dtype and gradient-reduction precision, TP/DP/CP/PP/VPP groups, global/effective tokens, microbatch/accumulation, rank-to-GPU/NIC placement, topology and collective sizes. Request original baseline traces and unprofiled step timing, all-rank memory and observed failures. Separate a declared future configuration from instantiated process groups and measured bottlenecks. Complete with an evidence-backed exposed-communication hypothesis or the missing observations needed to form one.
2. Check the requested and final effective TP settings separately. In the cited Bridge source an explicit TP overlap request can be disabled for TP<2, sequence_parallel=False or missing TE; TP overlap is experimental. Inspect the actual initialization/userbuffer path and supported shapes, dtypes, streams, bootstrap and buffer lifetimes. Named H100/B200 userbuffer presets belong to their specified shape/runtime, not arbitrary models. Passing configuration validation or finding TE installed does not demonstrate active overlap. Complete with a version-matched feasible candidate and the actual activation proof still required.
3. Keep ownership of DP settings explicit. The cited setup applies its optimizer/DDP overlap configuration through the Megatron DDP and distributed-optimizer path; another FSDP implementation is not the same consumer. The ordinary DP>1 preset uses a 128*1024*1024 parameter-count bucket, not bytes. Emerging optimizers have a distinct path that preserves existing Core/DDP bucket and gradient-reduction policy unless explicitly overridden; DP1 can still reduce across CP ranks. Trace actual normalization and overrides before proposing a bucket or overlap flag. grad_reduce_in_fp32 and fp8_param_gather belong to mixed precision; CUDA_DEVICE_MAX_CONNECTIONS and LayerNorm SM margins belong to launch configuration, not CommOverlapConfig fields. Complete with the final model/optimizer/DDP/launch values and their actual owners, or explicit unknowns.
4. For pipeline overlap, the cited default selects overlap_p2p_comm=True and batch_p2p_comm=False for PP>1 with VPP>1; without interleaving it selects batching instead, and PP1 needs neither. Explicit overrides still require the native schedule's validation. Check microbatch and pipeline layout, collective order, parameter gathering, checkpoint behavior and stream/event dependencies. Do not enable the source's deliberately disabled optimizer-step gather overlap merely because a flag exists. Complete with a finite schedule-aware intervention rather than a blanket instruction to turn every overlap option on.
5. Plan independent all-rank forward/loss, backward, accumulation and optimizer-update checks with fixed samples and precision tolerances; include supported graph/recompute/packing/checkpoint-resume combinations actually used. For performance compare warmed-up, unprofiled, paired end-to-end step/token windows and all-rank peak memory. Use matched traces to explain exposed wall time and interval unions, communication/compute intersection and SM/HBM/link contention; summing stream durations is not saved step time. More concurrency can slow each kernel and still change wall time in either direction. Complete with the exact candidate, independent gates, setup/communication-memory costs, stop/rollback conditions and handoff to the original trusted runner/owner. Preserve failed/no_gain/noise/unknown instead of adopting from a local bandwidth improvement.

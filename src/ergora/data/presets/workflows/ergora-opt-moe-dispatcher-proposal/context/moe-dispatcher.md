# MoE token-dispatcher proposal

This Ergora-authored offline direction resource uses the fixed sources below. It compares feasible dispatcher candidates for a fixed workload; a backend name or GPU family is not proof of initialization, correctness or a winning configuration.

1. Freeze exact model/routing/top-k/capacity/drop semantics, dtype, natural token skew, global batch and token accounting, TP/ETP/EP/DP/CP/PP groups and placement, graph/overlap/recompute scopes, framework/container/driver/CUDA/package identities, and actual GPU/NIC/NVLink/RDMA topology. Start from a working correctness baseline. Specify finite candidates and resource budgets for SMs, QPs, communication buffers, host/proxy work, warmup and trials. Complete with evidence-backed candidates or a list of facts preventing a comparison; hardware narrows candidates but never chooses a universal winner.
2. Follow the actual version's configuration and final hardware-validation path. The cited Bridge helper recognizes deepep, hybridep and ncclep as flex backends, while explicit None selects alltoall. For a real MoE model it sets both moe_token_dispatcher_type='flex' and moe_flex_dispatcher_backend and clears shared-expert overlap; a backend field alone is insufficient. Configuration is separate from validate_flex_dispatcher_backend on the training GPU after overrides. An unsupported final backend raises and is not silently replaced. Older Skill text describing hardware skip/fallback or only two backend names does not override this fixed implementation. Complete with the requested/effective configuration, actual validation/initialization evidence, and any inactive non-MoE request or failure.
3. Check imports, ABI, loaded library and the exact framework consumer on the actual target runtime, separately from the source helper's GPU allowlist. A recognized name or GPU check is necessary evidence, not package/API compatibility. The R3 research records a Core consumer of Buffer/ElasticBuffer while newer DeepEP mainline uses EPBuffer; do not install an unrelated latest release and infer compatibility. Treat NCCL EP and HybridEP requirements by their pinned runtime and topology; do not equate a nominal NVLink rank count with observed connectivity. Keep unsupported-package/import failures as environment limitations, not slower timing results. Complete with a compatible pinned candidate or a clear unmet dependency, never an implicit runtime replacement.
4. Plan independent all-rank token conservation with no unintended drops/duplicates, routing weights, dispatch/combine order, expert and input gradients, accumulation/optimizer updates and quality. Include supported empty/skewed experts, uneven token sizes, capacity boundaries, late ranks, stream/event order, buffer reuse and actual graph replay. Forced load balancing is a disclosed benchmark control that changes routing semantics; it cannot certify natural-routing convergence or interchange dropless/capacity baselines. Complete with actual oracle/tolerances, cases and original evidence or missing gates; an alltoall bring-up or finite loss alone does not validate the flex candidate.
5. Keep container, routing, batch, precision, PP/VPP, graph scope and overlap fixed for a dispatcher A/B; tune only a finite supported SM/buffer configuration with recorded failures. Measure warmed-up unprofiled paired step/token time, tail behavior, quality and all-rank memory, and use matching traces to explain exposed communication versus compute contention. Separate single-knob causal results from later multi-knob winners. Return an exact candidate with reasons to retain the baseline on no_gain/noise/failure, independent gates, total resource/setup cost and original-runner handoff. Full-group timeout/stop/recovery belongs to that owner; this proposal cannot terminate a subset of ranks, switch production backends or approve adoption.

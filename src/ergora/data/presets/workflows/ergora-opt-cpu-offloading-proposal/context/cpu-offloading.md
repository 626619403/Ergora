# CPU offloading proposal

This is an Ergora-authored offline synthesis. Select an actual offload mechanism and version; do not treat every CPU transfer as one portable switch or infer linear savings/slowdown from an upstream example.

1. Freeze the workload, full resolved config and matched Bridge/Core/TE/torch versions, device/rank mesh, peak phase and state ownership. Obtain per-rank device peaks and per-node host/NUMA/pinned capacity, CPU compute/thread limits, PCIe/NVLink transfer path and any actual NVMe budget. Unknown hardware, state or measurements blocks a concrete feasibility claim.
2. Distinguish these candidates and their native control owners:
   - Layer-level activation/optional weight offload uses `model.cpu_offloading*`. At the cited Core revision it requires PP=1, excludes recompute and fine-grained offload, and bounds offloaded layers below the total layer count. Use the conservative no-graph configuration unless the exact full-iteration exception and Bridge model spec/runner are independently verified; a Core validator exception alone does not establish that a Bridge path works.
   - Fine-grained activation offload uses its own module/fraction/group scheduling, can have PP/VPP and selected recompute support, and has graph/backend/version constraints. Its fraction is a choice over eligible groups/order, not a universal fraction of activation bytes. Warmup versus steady selection, pinned buffers and multiple in-flight microbatches affect peak host capacity and address lifetime.
   - Optimizer state/compute offload uses `optimizer.optimizer_cpu_offload`, the resolved fractional setting and `HybridDeviceOptimizer` path. It does not inherit the layer-level PP=1 rule. The cited implementation has precision-aware AdamW/decoupled-weight-decay requirements and distinct wrapper/FSDP branches; validate the actual optimizer, distributed/parameter-gather and precision recipe instead of declaring every optimizer or graph combination supported. CPU optimizer compute can dominate transfer overlap.
3. Choose at most a small owner-bounded set of legal fractions or layer/module boundaries, based on the component that actually limits the workload. Preserve baseline source/config, correct units and native validator failures. Separate fixed overhead, changed device state, extra pinned/host copies, CPU work and exposed transfer time; no extrapolated proportional-memory or linear-throughput promises. An NVMe/ZeRO interface or a native search loop is a different dependency, not automatically available through these Bridge flags.
4. Plan independent output/gradient/optimizer/checkpoint-restored-next-step checks as applicable, matched paired end-to-end throughput/latency and every relevant rank/node memory peak. Record transfer/compute overlap and contention with communication, graph capture, packing and recompute. Set wall/resource/trial limits and stop on invalid config, quality failure, OOM or unknown stop status; a search recommendation does not own stopping or recovery.
5. Return an explicit mechanism/compatibility matrix with source revision, assumptions and unverified cells, the smallest candidate set, required original artifacts and rollback/handoff to the trusted runner. Static suggestions, configuration acceptance, lower GPU occupancy or a short loss match are separate from measured long-run quality and overall benefit. Only the original owner can approve adoption.

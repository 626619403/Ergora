# Megatron FSDP state-sharding proposal

This Ergora-authored offline direction resource summarizes the fixed sources below. It is a readonly design and evidence-review contract, not an installed FSDP runtime or an executed training/checkpoint migration.

1. Identify the exact bottleneck by phase and rank, separating model/gradient/optimizer state from activations, workspaces and allocator/external use. Freeze model/data/optimizer/precision, current mesh, baseline state and desired recovery semantics. Compare DDP, distributed optimizer and fully sharded state against this evidence; activation pressure alone does not establish an FSDP benefit. Complete with a sourced state ledger and explicit unknowns.
2. Use the actual version's native configuration and wrapper. In the cited Bridge snapshot `ddp.use_megatron_fsdp` is the flag; the removed `dist.use_megatron_fsdp` field is invalid. A fully sharded candidate selects `ddp.data_parallel_sharding_strategy="optim_grads_params"`; inspect resolved optimizer/DDP flags and automatic setting changes rather than assuming the proposal was applied. Megatron FSDP, experimental `dist.use_torch_fsdp2` and MFSDP V2 are different paths with different support. Complete with the selected implementation, all effective overrides, stack identities and validator outcome, or a precise missing-support finding.
3. For the cited path check mutual exclusion with Torch FSDP2, unsupported `dist.use_tp_pp_dp_mapping`, actual optimizer support and `CUDA_DEVICE_MAX_CONNECTIONS` requirements, communication registration/buffer rules and the chosen dense/expert sharding strategies. Use the workload's native checks for TP/PP/CP/EP, precision, graph, recompute and offload combinations; configuration-level support does not establish every combination's correctness or speed. Request actual resolved settings and execution evidence. Complete when each relevant constraint has its source, result or unverified dependency.
4. For save/load require the matching `fsdp_dtensor` DTensor/DCP path and complete metadata; it is not directly interchangeable with a non-FSDP `torch_dist`/zarr checkpoint. A public recipe may still default to the wrong format. Treat documented resharding as a capability to verify for the exact source/target layouts, not an exact-resume guarantee. Check weights, optimizer shards/step/LR, RNG, dataloader membership/order and processed tokens after restoring a next update. Record partial-load behavior, missing buffers and irreproducible RNG changes explicitly. Complete with a migration/recovery matrix, checkpoint identity and a rollback target, keeping unexecuted rows pending.
5. Bound a baseline/candidate comparison with independent numerical/quality gates and matched global update semantics. Request startup/first-update/steady/eval/checkpoint/resume memory for all relevant ranks, exposed all-gather/reduce-scatter cost, paired step/token timing and total save/load/setup costs. Lower state memory, a finite loss or one successful load alone cannot establish throughput, quality or faithful recovery. Return a proposal plus missing evidence and stop/rollback conditions; the original trusted runner and owner retain execution, recovery and adoption.

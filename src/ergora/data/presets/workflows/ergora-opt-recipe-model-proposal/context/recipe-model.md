# Model and recipe proposal contract

This project-authored resource synthesizes fixed Bridge knowledge. Selecting it neither installs Bridge/ModelOpt/RD-Agent nor downloads weights, executes remote model code, searches configurations or launches training. Its role is to select a justified starting point and expose missing model/recipe evidence; code adaptation goes through the existing six-stage developer, and experiments through the original trusted runner.

1. Freeze the requested task (pretrain, SFT, PEFT, evaluation, inference or a specified RL framework), exact model family/variant/config, checkpoint revision and weight format, tokenizer/processor/data revisions and licenses, modalities, objective, precision, sequence/token/batch and optimizer contract. Inventory actual supplied bytes separately from desired specifications and upstream reports. Record available hardware/topology and exact framework/Core/TE/PyTorch/CUDA/container tuple; an existing registration or exported recipe is not initialized runtime support. Remote-code trust, gated downloads and model/data access require the original owner, not implicit permission from a URL. Complete with a justified exact recipe/model starting point or a minimal unresolved input request.
2. Distinguish library functional recipes from canonical performance recipes and their actual entry point. The pinned library uses scripts/training/run_recipe.py; benchmark entry points have different defaults and dataset/override semantics. Mock data, forced balancing, disabled correctness checks and timing-only schedules are benchmark-only evidence, not real convergence. Do not pair a pretrain-only mock preset with SFT/PEFT merely because it launches. Inspect the exact exported callable and resolved ConfigContainer instead of guessing flags from another version. Complete with the path/version/mode and explicit canonical versus modified status, without claiming execution.
3. Freeze convergence semantics before proposing execution layouts. Check starting weights/trainable parameters, data split/order/seeds, tokenizer/mask/truncation/packing, sequence/global batch/token horizon, loss/routing/token-dropping, optimizer/LR/schedule/dropout/precision/PEFT. Changing these creates a new convergence experiment. Parallel mesh, recompute/offload, overlap/fusion/graphs and unchanged-routing transport may preserve semantics but still require numerical sentinels. Microbatch/accumulation are execution fingerprints only while effective batch membership/order, normalization, update boundaries and token count remain fixed. Do not rank absolute losses across tokenizers/architectures or change batch/quality settings merely to meet a throughput target. Complete with a finite candidate set, changed versus invariant fields and independent correctness/quality gates.
4. For new architecture support, inspect the HF implementation/config and the exact existing bridge, hf_config_to_model_config_kwargs(), mapping_registry() and builder-backed ModelConfig. The pinned Qwen3 config path is an example, not proof that all older provider-based models should be mechanically rewritten. Preserve complete parameter mapping, tied embeddings, QKV/expert layout, norms, bias/rotary/attention behavior, precision and architecture-specific tensor transforms. Reuse existing building blocks; missing computation or composition needs scoped code, real callers and developer review. Config construction, toy roundtrip or exporting some tensors does not prove full checkpoint/model support. Complete with exact mapping/implementation gaps and an existing six-stage handoff, not a new code-generation runner.
5. Treat VLM/audio/video as separate requested consumers. Inspect nested language versus modality config, tie_word_embeddings placement, actual processor outputs, positions/masks, modality insertion/projector, freeze policy, placement and gradient synchronization. Pinned guidance favors the appropriate HF perception encoder for new wrappers; an older native tower is not a universal requirement. A passing text prompt does not activate or verify requested modalities. Complete with activated modality cases and explicit unsupported/unverified paths, not generic multimodal support.
6. Separate lossless conversion, forward correlation, deterministic generation, finite training, export, checkpoint/RNG/data/optimizer resume and independent task quality. HF deployment export is not a full training checkpoint. Pair MLM/Bridge mock comparisons only with matched initialization, data order, seed, loss, LR horizon and precision; finite BF16 closeness needs a frozen tolerance and does not prove convergence. Verification-card status and helper exit0 are declarations/operation outcomes until actual results are consumed. For each claim require exact original artifacts and the appropriate independent check; return gaps rather than inventing weights or measurements.
7. Structural pruning/distillation, quantization and ordinary execution tuning are different experiments. R9 identifies ModelOpt Minitron/Puzzletron native workflows and a text-SFT FT-Agent, not installed universal architecture Agents; no such execution is added here. Their candidate structure, teacher/student co-residency, modalities, mesh/export constraints, independent holdout, budget, native session and recovery need separately accepted consumers. RL rollout/reward/refit/checkpoint stays with the chosen external framework. Never multiply local speedups or borrow another version's compatibility. Complete with original tool/owner handoff and unchanged evidence/adoption authority.
